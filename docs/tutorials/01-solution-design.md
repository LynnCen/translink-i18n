# 解决方案设计：架构决策与权衡

> **架构是关于权衡的艺术，没有银弹，只有 trade-off。**

上一章分析了国际化的五个核心问题。本章将针对每个问题，阐述设计决策及其背后的原理。

---

## 设计原则

在展开具体方案之前，先明确指导原则：

1. **关注点分离**（Separation of Concerns）：每个模块只解决一个问题
2. **开放封闭原则**（Open-Closed Principle）：对扩展开放，对修改封闭
3. **依赖倒置**（Dependency Inversion）：核心不依赖细节，细节依赖抽象
4. **渐进增强**（Progressive Enhancement）：最小可用 → 按需扩展

---

## 问题一：Key 管理 → 内容寻址

### 设计决策

**用内容哈希替代人工命名的 Key。**

```javascript
// 传统：人工定义 Key
t('dashboard.welcome.title')

// 新方案：内容即 Key
$tsl('欢迎使用')  // → hash('欢迎使用') → 'a1b2c3d4'
```

### 原理：内容寻址（Content Addressing）

这个思想来自分布式系统：**用内容的哈希值作为其唯一标识**。

- Git 用 SHA-1 标识每个 commit
- IPFS 用内容哈希作为文件地址
- Docker 用 digest 标识镜像层

**优势**：
- **天然唯一**：相同内容 = 相同哈希，自动去重
- **无需命名**：消除命名规范的心智负担
- **可追溯**：哈希与内容绑定，不会出现「Key 存在但内容不匹配」

### 边界情况处理

**同文本不同语境**：

```javascript
$tsl('保存', { context: 'button' })  // 动词：Save
$tsl('保存', { context: 'noun' })    // 名词：Saving
```

哈希计算时加入上下文：`hash('保存::button')` ≠ `hash('保存::noun')`

## 问题二：协作流程 → 多工作流适配

### 设计决策

**不改变用户的工具习惯，用 CLI 作为「数据转换枢纽」。**

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│   开发者    │     │    运营     │     │   翻译团队  │
│   JSON/Git  │◄───►│   Excel     │◄───►│   云平台    │
└─────────────┘     └─────────────┘     └─────────────┘
        ↑                  ↑                  ↑
        └──────────────────┼──────────────────┘
                           │
                    CLI 统一转换
```

### 原理：适配器模式（Adapter Pattern）

核心数据模型是 JSON，其他格式通过适配器转换：

```bash
# JSON ↔ Excel
translink export --format excel
translink import --format excel

# JSON ↔ 云平台
translink push --to vika
translink pull --from vika
```

**关键设计**：
- **单一数据源**：JSON 是 Source of Truth
- **增量同步**：只同步差异，不全量覆盖
- **冲突检测**：导入前检查版本一致性

## 问题三：框架耦合 → 核心引擎 + 适配器

### 设计决策

**将翻译引擎设计为框架无关的纯逻辑，通过适配器接入具体框架。**

```
┌─────────────────────────────────────────┐
│           I18nEngine（Pure）             │
│                                         │
│  · translate(key, params): string       │
│  · changeLanguage(lang): void           │
│  · onLanguageChange(callback): void     │
└─────────────────────────────────────────┘
              ↓                ↓
      ┌──────────────┐  ┌──────────────┐
      │ Vue Adapter  │  │React Adapter │
      │  useI18n()   │  │  useI18n()   │
      │  响应式绑定   │  │  状态更新    │
      └──────────────┘  └──────────────┘
```

### 原理：依赖倒置原则

- **高层模块**（Vue/React 组件）不依赖低层模块（翻译引擎实现）
- **两者都依赖抽象**（I18nEngine 接口）

**收益**：
- 更换框架只需更换适配器
- 核心引擎可独立测试
- 翻译资源可跨框架共享

## 问题四：构建优化 → Vite Plugin 深度集成

### 设计决策

**让翻译成为构建流程的一等公民。**

| 能力 | 实现方式 |
|-----|---------|
| 代码转换 | `$tsl('文本')` → `t('hash')` |
| 懒加载 | 每种语言独立 chunk |
| Tree-shaking | 移除未使用的翻译条目 |
| HMR | 翻译文件变更即时生效 |

### 原理：编译时优化 vs 运行时开销

```
开发时            构建时              运行时
源代码    →    Vite Plugin    →    优化后代码

$tsl('欢迎')   代码转换         t('a1b2c3d4')
              哈希预计算         直接查表
```

**将计算从运行时前移到构建时，降低用户侧的性能开销。**

## 问题五：AI 翻译 → Provider 抽象 + 智能调度

### 设计决策

**抽象 AI Provider 接口，实现批量优化和缓存策略。**

```
┌─────────────────────────────────────────┐
│         AITranslationManager            │
├─────────────────────────────────────────┤
│  · 增量检测：只翻译新增/修改的文本        │
│  · 结果缓存：相同文本不重复翻译           │
│  · 批量优化：多条文本合并为单次 API 调用  │
└─────────────────────────────────────────┘
                    ↓
┌──────────┬──────────┬──────────┬──────────┐
│ OpenAI   │ DeepSeek │ Gemini   │ Claude   │
│ Provider │ Provider │ Provider │ Provider │
└──────────┴──────────┴──────────┴──────────┘
```

### 原理：策略模式（Strategy Pattern）

AI Provider 是可替换的「策略」：

```typescript
interface AIProvider {
  translate(params: TranslateParams): Promise<TranslateResult>
  translateBatch?(params: BatchParams): Promise<BatchResult>
}
```

**切换 AI 平台 = 切换配置，代码零修改。**

## 整体架构

```
┌─────────────────────────────────────────────────────────────┐
│                    TransLink I18n                            │
├─────────────────┬─────────────────┬─────────────────────────┤
│      CLI        │    Runtime      │      Vite Plugin        │
│    开发时工具    │    运行时引擎    │       构建时优化         │
├─────────────────┼─────────────────┼─────────────────────────┤
│  · AST 提取     │  · 翻译查找     │  · 代码转换             │
│  · 哈希生成     │  · 参数插值     │  · 虚拟模块             │
│  · 多格式导出   │  · 语言切换     │  · 懒加载分包           │
│  · AI 翻译     │  · 缓存管理     │  · HMR 热更新           │
│  · 插件扩展     │  · 框架适配     │  · Tree-shaking        │
└─────────────────┴─────────────────┴─────────────────────────┘
```

### 架构特性

| 特性 | 说明 |
|-----|------|
| **独立部署** | 三个包独立发布，按需安装 |
| **松散耦合** | 包之间通过接口通信，无直接依赖 |
| **渐进增强** | 最小化只需 Runtime；完整体验加上 CLI + Plugin |

---

## 设计权衡

| 决策 | 收益 | 代价 |
|-----|------|------|
| 内容哈希 | 自动去重、无需命名 | 哈希碰撞风险（可控） |
| 三包分离 | 按需安装、职责清晰 | 版本协调复杂度 |
| 框架适配器 | 迁移成本低 | 多一层抽象 |
| 构建时转换 | 运行时性能好 | 需要 Vite 环境 |

**没有完美的架构，只有适合场景的权衡。**
