# 前端国际化的工程困境

> **在软件工程中，理解问题的本质比解决问题更重要。**

国际化（Internationalization，简称 i18n）看似简单——不就是把「欢迎」换成「Welcome」吗？

但当你真正在生产环境中实施时，会发现这是一个**系统性工程问题**，而非简单的文本替换。

---

## 问题空间分析

### 问题一：翻译标识符的管理困境

国际化的核心机制是**间接引用**：代码不直接包含文本，而是引用一个标识符（Key），由运行时根据当前语言环境解析为实际文本。

```javascript
// 间接引用模式
t('dashboard.welcome')  // Key → 运行时查表 → '欢迎'
```

这个设计的问题在于：**Key 是人工定义的元数据，而人工维护的元数据必然会腐化。**

#### 腐化的表现形式

**命名空间混乱**：

```javascript
// 同一个项目，四种命名风格
t('dashboard.welcome')        // 层级命名
t('welcomeMessage')           // 驼峰命名
t('WELCOME_MSG')              // 常量命名
t('page_home_title_welcome')  // 下划线 + 路径
```

三个月后，没有人知道新增的 Key 应该遵循哪种规范。

**语义断裂**：

```javascript
t('err_10086')  // 这是什么错误？必须查表才知道
```

代码的可读性降为零。维护者看到 Key，无法直接理解业务含义。

**一致性失效**：

```javascript
// 同一个「保存」，被定义了四次
t('common.save')
t('form.saveBtn')
t('action.save')
t('button.save')
```

翻译成本 ×4，且未来修改时容易遗漏。

**本质问题**：Key 是代码与翻译之间的「契约」，但这个契约是**隐式的、脆弱的、依赖人工维护的**。

---

### 问题二：多角色协作的流程断裂

国际化涉及多个角色：开发者、翻译人员、产品运营。他们使用不同的工具：

| 角色 | 工具 | 数据格式 |
|-----|------|---------|
| 开发者 | IDE + Git | JSON/YAML |
| 翻译人员 | Excel/Google Sheets | 表格 |
| 产品运营 | 内部系统 | 数据库 |

**流程断裂场景**：

```
Day 1: 开发者导出 translations.xlsx
Day 2: 翻译开始工作
Day 3: 另一个开发者新增 20 条文案，重新导出
Day 4: 翻译完成，提交旧版本
Day 5: 导入时覆盖了 Day 3 的新增内容
```

**本质问题**：Excel 是**单用户编辑模型**，不支持并发协作、版本控制、冲突检测。用错误的工具解决协作问题，必然导致流程断裂。

---

### 问题三：框架耦合导致的迁移成本

传统 i18n 库（vue-i18n、react-i18next）的设计是**框架优先**的：

```javascript
// Vue 2
this.$t('key')
this.$i18n.locale = 'en'

// Vue 3 Composition API
const { t, locale } = useI18n()
locale.value = 'en'

// React
const { t, i18n } = useTranslation()
i18n.changeLanguage('en')
```

**每个框架一套 API，每次升级一次迁移。**

更严重的是，如果项目需要同时支持多个框架（如微前端场景），翻译资源无法共享，逻辑无法复用。

**本质问题**：翻译引擎（查表 + 插值）是**业务无关的纯逻辑**，不应该与 UI 框架耦合。耦合导致了不必要的迁移成本。

---

### 问题四：构建时优化的缺失

翻译文件通常被视为「静态资源」，直接打包：

```javascript
import zhCN from './locales/zh-CN.json'  // 200KB
import enUS from './locales/en-US.json'  // 200KB
import jaJP from './locales/ja-JP.json'  // 200KB
// 用户只看中文，却下载了 600KB
```

**问题清单**：

1. **全量加载**：所有语言包一次性加载，无论用户是否需要
2. **无法 Tree-shaking**：未使用的翻译条目无法被移除
3. **无 HMR 支持**：修改翻译后需要手动刷新

**本质问题**：翻译文件没有参与现代构建工具的优化流程。

---

### 问题五：AI 翻译的成本失控

使用大语言模型进行翻译时，常见的做法是：

```javascript
for (const text of allTexts) {
  await translateWithAI(text)  // 1000 次 API 调用
}
```

**成本问题**：

| 场景 | API 调用 | 系统提示词 Token | 成本 |
|-----|---------|----------------|------|
| 1000 条逐条翻译 | 1000 次 | 1000 × 50 = 50000 | $5.00 |
| 新增 10 条，重新全量翻译 | 1010 次 | 50500 | $5.05 |

**本质问题**：缺乏**增量翻译**（只翻译新增/修改的）、**结果缓存**（相同文本不重复翻译）、**批量优化**（合并请求减少开销）。

---

## 问题本质的抽象

| 问题 | 表象 | 本质 |
|-----|------|------|
| Key 管理混乱 | 命名不统一、遗漏、重复 | 人工维护隐式契约 |
| 协作流程断裂 | 版本覆盖、冲突丢失 | 工具模型不匹配 |
| 框架迁移成本 | API 不兼容 | 业务逻辑与框架耦合 |
| 构建优化缺失 | 体积大、加载慢 | 未参与构建流程 |
| AI 成本失控 | 重复翻译、无缓存 | 缺乏智能调度 |

---

## 设计目标

基于以上分析，一个良好的国际化方案应该：

1. **消除隐式契约**：Key 应该从内容自动生成，而非人工定义
2. **适配多工具链**：支持开发者的 JSON、运营的 Excel、团队的云端
3. **解耦框架依赖**：核心引擎框架无关，通过适配器接入
4. **参与构建优化**：懒加载、Tree-shaking、HMR
5. **智能翻译调度**：增量检测、结果缓存、批量请求
